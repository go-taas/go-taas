## 1. 背景与竞品调研

### 1.1 为什么现在做服务配额管理

平台的防护轨道今天是单维的。功能 #6 给了按 Key 的**速率限制**（RPM/TPM — 一个 Key 可以调多*快*）与组织**支出上限**（一个组织每月最多烧*多少钱*），其 non-goals 明确将"按 Key 的 QPS 或并发限制、按模型或按端点的速率限制、速率限制层级或套餐"推迟到后续功能。功能 #5 的多租户同样延迟了"组织/项目配额"。

仍然缺失的是**资源维度**：一个组织可以同时保持多少在途请求（并发）、可以部署多少推理服务、每天可以提交多少批量任务、单个请求最多生成多少 token。没有这些，一个租户就能饿死整个机群 — 一波长时间运行流式请求会占住 GPU，而弹性伸缩（#16）会乐意为它扩容*上去*（租户付钱，但机群的 GPU 没了）；一个租户可以部署 50 个空闲服务；一个失控的智能体循环可以永远生成 8192 token 的补全。速率限制抓不住其中任何一个：每分钟 60 个持续 10 分钟的流式请求，就是 60 个被无限期占用的并发槽位。

每个竞品平台都显式分离这些轴。本功能新增**按组织的资源配额** — 四个有界维度、运营者配置、在网关（并发、单请求 token）与控制面（服务数、每日批量）失败即拒执行，并配租户可见的配额条，让约束透明而非神秘。

### 1.2 访问模式：平台管理的组织配额 vs 备选方案

| 模式 | 是什么 | 采用 / 拒绝理由 |
| --- | --- | --- |
| **平台管理的按组织资源配额，网关 + 控制面执行**（采用） | 运营者为每个组织配置四个配额维度（并发、服务数、每日批量、单请求输出 token）；`VerifyAPIKey` verdict 携带它们到网关，网关本地执行热路径维度；控制面在创建时执行生命周期维度。 | 唯一能保护**机群**（而不只是账单）的模式：并发与 token 上限是只有数据面能及时执行的资源守卫，服务数与批量数是只有控制面能看到的生命周期守卫。原样复用 #6 的 verdict 搭载契约 — 热路径零新增 RPC。 |
| 配额套餐 / 计划（免费版：2 个服务，专业版：20 个……） | 预打包的配额包分配给组织。 | v1 拒绝：套餐是相同四个字段之上的**打包**决策；先交付原始的按组织字段保持执行诚实可测，套餐预设只是 UI 便利（D5）而非数据模型。 |
| 租户自助配额管理 | 租户自己提升配额（可能付费）。 | 拒绝：配额是保护机群*免受*租户影响的；被限制的一方不能持有杠杆。配额变更仅限运营者（D7）。 |
| 按 Key 配额 | 配额维度挂在 API Key 上。 | 拒绝：资源轴（并发、服务数、批量任务）是**组织级**事实 — 持有两个 Key 的租户会让每个限额翻倍。Key 保留 #6 的 RPM/TPM；组织获得本功能的资源配额（D2）。 |
| 纯超额计费（无硬上限） | 放任使用并计费。 | 资源轴拒绝：钱买不回被其他租户等待的 GPU。支出保留资金轴（#6/#8）；资源获得失败即拒的硬上限（§1.4）。 |
| 扩展 #6 的速率限制字段 | 把并发加进 Key 的 RPM/TPM 对。 | 拒绝：主体不同（组织 vs Key）、执行点不同（在途跟踪 vs 令牌桶）、错误语义不同（排队拒绝 vs 节流）。独立的组织配额对象让两者分别可查（D1）。 |

| 产品 | 配额模式 | go-taas 决策 |
| --- | --- | --- |

| **AWS Bedrock** | 按账户的模型调用配额（TPS）在 Service Quotas 控制台管理，带**申请提升**流程；每区域默认配额 | 采纳管理页的 **Service Quotas 控制台形态**（按组织行、编辑对话框、变更历史）与申请提升**链接**（mailto 通知运营者 — v1 无自助审批流）；**拒绝**审批工作流（单运营者平台，运营者直接改） |

| **SiliconFlow** | 按 Key 的并发限制展示在 Key 详情页；硬 429 式拒绝并附清晰中文错误信息 | 采纳**并发作为头条维度**并配显式、有文档的拒绝错误 — 中文 LLM 平台最先标准化的维度 |
| **Modal / Baseten** | 按工作空间的并发副本或 GPU 上限；按套餐的部署数限制 | 采纳**服务数维度**（go-taas 对应部署上限的概念）与失败即拒的创建拒绝、错误文案中带当前计数 |

### 1.4 失败即拒资源守卫不变式

核心产品规则：

1. **配额保护机群，不保护账单。** 四个维度是资源轴；资金（支出上限、余额）留在 #6/#8 并独立组合 — 一个请求可以通过配额但资金失败，或通过资金但配额失败。
2. **执行失败即拒且即时。** 并发与单请求 token 在网关、请求到达服务**之前**执行；服务数与每日批量在创建时执行。配额拒绝绝不排队、绝不等待、绝不部分执行。
3. **三个错误，绝不混淆。** 配额拒绝（133xx 块）区别于速率限制 429（#6）与资金 402（#8）— SDK 作者能分辨撞上了哪根杠杆。网关检查顺序：速率限制 → 配额 → 资金（被节流的 Key 不会到达配额检查；被配额拦截的请求不会到达资金检查）。
4. **0 = 不限，默认宽松。** 未设置或零配额表示该维度无限制（#6 惯例）；新组织默认不限，运营者审慎收紧。
5. **配额对被约束方可见。** 租户看到自己的配额条（每维度当前用量 / 限额）— 租户看不见的限额与故障无法区分。

### 1.5 决策与范围

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | **新管理板块** `/admin/quotas` + `/api/v1/admin/quotas/*` 负责管理，新终端用户页 `/quotas` + `/api/v1/quotas/*` 负责租户自己的视图 — **不是** #6 速率限制编辑器或 #5 组织编辑器的扩展 | 配额是独立的对象类（组织级资源轴，有自己的执行点与历史）；专属页面让 #6 的 Key 级节流与本功能的组织级资源分别可查（§1.2） |
| D2 | **组织上的四个配额维度**：`max_concurrent_requests`（0 = 不限，默认 0；设置时 1–10000）、`max_inference_services`（0 = 不限，默认 0；设置时 1–1000）、`max_batch_jobs_per_day`（0 = 不限，默认 0；设置时 1–10000）、`max_output_tokens_per_request`（0 = 不限，默认 0；设置时 64–32768）。四个都是**按组织**，不是按 Key（§1.2） | 平台真正可能被饿死的四个资源轴：在途请求、已部署服务、每日批量提交、单请求生成。有界范围保持取值合理；0 = 不限保持默认宽松（§1.4） |
| D3 | **热路径维度搭载 `VerifyAPIKey` verdict**，与 #6 的 RPM/TPM 完全一致：verdict 增加 `max_concurrent_requests` 与 `max_output_tokens_per_request`；网关按组织跟踪在途请求（接受时递增，完成时递减）并在分发前通过钳制/校验请求的 `max_tokens` 执行 token 上限。生命周期维度（`max_inference_services`、`max_batch_jobs_per_day`）由 `infer` 与 `batch` 在创建时执行 | 热路径零新增 RPC（#6 契约模式）；在途跟踪是网关本地状态，唯一能看到接受/完成的地方；创建时检查天然属于控制面。verdict 缓存 TTL（30 秒）限定配额变更传播 — 在抽屉中文档化 |
| D4 | **配额拒绝失败即拒，使用专属错误块 133xx**：**13301 `CodeQuotaConcurrencyExceeded`**（HTTP 429 + `Retry-After`）、**13302 `CodeQuotaServiceCountExceeded`**、**13303 `CodeQuotaBatchJobsExceeded`**、**13304 `CodeQuotaOutputTokensExceeded`**（HTTP 400）、**13305 `CodeQuotaInvalid`**（校验）、**13306 `CodeQuotaNotFound`**。并发拒绝携带 `Retry-After: 1`（在途窗口很短）；其余为即时 4xx | 三错误绝不混淆（§1.4）：配额 ≠ 速率（10037）≠ 资金（10502）。429 与 400 的区分映射语义：并发是瞬态（稍后重试），其余是配置（改请求或改配额） |
| D5 | **管理页提供套餐预设仅作便利**：Default（全部不限）、Starter（10 并发 / 3 服务 / 每日 5 批量 / 4096 token）、Growth（50 / 20 / 50 / 8192）、Enterprise（200 / 100 / 500 / 16384）。选择预设填充表单；运营者保存前可编辑任意字段。预设是 UI 常量，不是数据模型（§1.2） | 运营者要配置几十个组织；预设加速常见场景而不冻结模型。原始字段仍是事实来源 |
| D6 | **配额变更在 verdict 缓存 TTL 内生效**（热路径维度 ≤ 30 秒），生命周期维度即时；抽屉文档化传播窗口。收紧配额到当前用量之下**不会**杀掉在途请求或删除服务 — 只阻塞新的（用量自然排空） | 可预测、非破坏性收紧：守卫在边界阻塞，绝不撤销已在运行的东西 — 与 #6 支出上限对在途请求的语义相同 |
| D7 | **配额管理仅限运营者**；租户面只读（配额条 + `/quotas`）。租户"申请提升"是发往运营者的 **mailto 链接**（可配置地址），不是工作流（§1.3 Bedrock） | 被约束方不能持有杠杆（§1.2）；mailto 覆盖单运营者平台而无需审批流栈 |
| D8 | **租户配额条展示全部四个维度**（当前用量 / 限额，或"不限"）于终端用户控制台（组织上下文区的紧凑条 + `/quotas` 详情页）；用量计数为：在途请求（网关）、服务数（infer）、今日批量任务（batch）、单请求 token 上限（常量展示）。任何租户看不到其他组织的配额 | 撞上之前可见（§1.3 Anthropic）；配额条让约束透明、13301 错误可诊断 |
| D9 | **所有配额变更均审计**（`quota.updated` 带旧 → 新值与操作运营者），管理页展示按组织的变更历史（最近 20 条） | 配额变更是有公平性影响的机群保护决策；历史匹配审计惯例（#22）并回答"谁在何时收紧的" |
| D10 | **Realm 与表面绑定**：管理仅限管理面（`/admin/quotas` + `/api/v1/admin/quotas/*`）；租户视图是终端用户面（`/quotas` + `/api/v1/quotas/*`）。用户 realm 会话访问管理路由得到 **10038**；无角色会话得到 **10036** | 与控制台表面分离（#17）一致；配额内部信息（全平台对比）是运营者知识，本组织的配额是租户的 |

**范围内**：四个组织配额字段及其执行（网关在途跟踪 + token 上限；infer 服务数检查；batch 每日检查）；管理页 `/admin/quotas`（带配额列的组织表、带预设的编辑对话框、变更历史抽屉）；租户配额条与 `/quotas` 页；verdict 缓存扩展；审计事件；申请提升 mailto。

**范围外**（由其他功能跟踪或明确排除）：按 Key 配额（明确排除 — 仅组织级，§1.2/D2）、作为数据模型的配额套餐/计划（D5 — 预设是 UI 常量）、租户自助配额变更与审批工作流（明确排除，D7）、项目级配额（随 #5 项目模型延迟）、按模型或按端点配额（未来 — 先做组织轴）、配额超额计费（明确排除 — 硬上限，§1.4）、速率限制 RPM/TPM 与支出上限（功能 #6，原样复用）、资金/余额执行（功能 #8，原样复用）、弹性伸缩交互（伸缩仍在组织服务配额内进行；配额封*天花板*，#16 封*行为*）。

## 2. 用户角色

| 角色 | 描述 | 与配额的交互 |
| --- | --- | --- |
| **平台管理员** | 运营 go-taas 平台的运营者 | 打开 `/admin/quotas` → 审查按组织配额行 → 编辑组织配额（直接或经预设） → 查看变更历史 → 回复申请提升邮件 |

> 术语：消费侧调用者称为**智能体**（Agent），与仓库惯例一致。配额条与 `/quotas` 页是租户观察限额的窗口 — 否则限额在撞上之前不可见。

## 4. 功能需求

### FR1 — 配额模型与配置

- **FR1.1** 组织配额为 `{organization_id, organization_name, max_concurrent_requests (int64, 0 = 不限, 否则 1–10000), max_inference_services (int64, 0 = 不限, 否则 1–1000), max_batch_jobs_per_day (int64, 0 = 不限, 否则 1–10000), max_output_tokens_per_request (int64, 0 = 不限, 否则 64–32768), updated_at, updated_by}`。组织创建时默认：全部 0（不限，§1.4）。
- **FR1.2** `ListOrganizationQuotas`（`GET /api/v1/admin/quotas`）返回按组织配额行及当前用量（`concurrent_requests`（实时）、`inference_services`、`batch_jobs_today`），支持 `page_size`/`page_token` 分页、`name` 搜索与 `unlimited_only` / `limited_only` 过滤。用量计数是尽力而为的快照（在途计数是经配额 RPC 中继的网关状态）。
- **FR1.3** `GetOrganizationQuota`（`GET /api/v1/admin/quotas/{organization_id}`）返回单个组织的配额、用量与最近 20 条变更历史。未知组织返回 **13306 `CodeQuotaNotFound`**。
- **FR1.4** `UpdateOrganizationQuota`（`PATCH /api/v1/admin/quotas/{organization_id}`）设置四个维度的任意子集。超出范围的值（或负数）返回 **13305 `CodeQuotaInvalid`** 并在消息中指名维度。收紧到当前用量之下是允许的且非破坏性（D6）。变更被审计（`quota.updated`，旧 → 新，运营者）并出现在历史中。
- **FR1.5** 编辑对话框提供四个预设（D5）一键填充；选择预设填充字段后运营者可在保存前编辑。预设是 UI 常量，标注"Default / Starter / Growth / Enterprise"。

### FR2 — 执行：热路径维度（网关）

- **FR2.1** `VerifyAPIKey` verdict 增加 `max_concurrent_requests` 与 `max_output_tokens_per_request`（组织级，随 verdict 缓存，TTL ≤ 30 秒 — D3）。网关像今天读 RPM/TPM 一样读取它们。
- **FR2.2** **并发**：网关维护按组织的在途计数器（请求被接受分发时递增，完成时递减 — 流结束、错误或客户端断开）。当组织计数器达到限额时，新请求被拒 **13301 `CodeQuotaConcurrencyExceeded`**、HTTP 429、`Retry-After: 1`。检查在 #6 速率限制检查**之后**、资金检查**之前**运行（§1.4 顺序）。不限（0）跳过检查。
- **FR2.3** **单请求输出 token**：当组织的 `max_output_tokens_per_request` 已设置，`max_tokens` 超出它的请求被拒 **13304 `CodeQuotaOutputTokensExceeded`**、HTTP 400，消息中指明上限（"每个请求上限 N token"）；未显式携带 `max_tokens` 的请求以钳制到上限的 `max_tokens` 分发（钳制是默认行为 — 只有显式超上限值被拒绝）。检查与并发检查一起运行。
- **FR2.4** 网关向配额 RPC（FR1.2）暴露按组织在途计数器用于用量快照；网关重启将计数器重置为实时真值（在途请求尽可能从活跃流重新推导，否则从零开始 — 窗口受 verdict TTL 与流时长限定，文档化为尽力而为）。

### FR3 — 执行：生命周期维度（控制面）

- **FR3.1** **服务数**：`CreateInferenceService`（及部署路径）对照组织的当前服务数检查 `max_inference_services`；达到或超过限额时创建被拒 **13302 `CodeQuotaServiceCountExceeded`**，消息指明当前计数与限额。不限（0）跳过检查。收紧绝不删除已存在服务（D6）。
- **FR3.2** **每日批量任务**：`CreateBatchJob` 对照自本地午夜以来的任务数检查 `max_batch_jobs_per_day`；达到或超过限额时创建被拒 **13303 `CodeQuotaBatchJobsExceeded`**，消息指明今日计数与限额。不限（0）跳过检查。已取消与失败的任务仍计数（守卫针对提交而非成功）。
- **FR3.3** 两个生命周期检查都在现有创建事务内运行（无新 RPC）；拒绝文案面向用户且可操作（"您的组织已达到 N 个推理服务的上限。请申请提升或移除未使用的服务。"）。

### FR4 — 租户面：配额条与详情页

- **FR4.1** `GetMyQuota`（`GET /api/v1/quotas`）返回调用者组织的配额与实时用量：`{max_concurrent_requests, current_concurrent_requests, max_inference_services, current_inference_services, max_batch_jobs_per_day, batch_jobs_today, max_output_tokens_per_request}` — 0 渲染为"不限"。任何字段不含其他组织的数据。
- **FR4.2** 终端用户控制台展示**配额条**（组织上下文区的紧凑条）：每维度"用量 / 限额"带进度条（或"不限"），≥ 80% 变琥珀色、100% 变红色。配额条链接到 `/quotas`。
- **FR4.3** `/quotas` 页将四个维度展示为卡片（当前用量、限额、进度条与通俗说明："当前在途请求数"、"已部署推理服务"、"今日已提交批量任务"、"单请求最大输出 token"），外加**申请提升**按钮（mailto 到已配置的运营者地址并预填组织名 — D7）。页面提供加载、空态（全部不限 — 友好的"您的组织未设置任何限额"）与错误状态。
- **FR4.4** 租户面**没有**配额变更 — 页面与配额条只读（D7）。

### FR5 — 表面、realm 与 API 绑定

- **FR5.1** 管理仅限管理面（`/admin/quotas` + `/api/v1/admin/quotas/*`）；租户视图是终端用户面（`/quotas` + `/api/v1/quotas/*`）。用户 realm 会话访问管理路由得到 **10038 `CodeRealmMismatch`**；无 platform-admin 角色的会话得到 **10036 `CodeForbidden`**。
- **FR5.2** 管理页渲染：组织表（组织、并发（用量/限额）、服务（用量/限额）、今日批量（用量/限额）、Token 上限、更新时间、更新人）、搜索与过滤、编辑对话框（预设 + 四个字段及校验文案）、变更历史抽屉（时间、运营者、维度、旧 → 新）。全部状态：加载、空态、错误、无权限。
- **FR5.3** 所有配额变更被审计（FR1.4）；列表/读取调用不审计，与平台读路径惯例一致。
- **FR5.4** 网关执行契约（FR2）**钉在本文档中**并经合成验证（仓库外数据面组件的既定模式）：verdict 字段、检查顺序（速率 → 配额 → 资金）、错误码与 `Retry-After` 头是契约；compose 栈的 mock 网关为 e2e 遵守它们。

### 5.2 页面映射

| --- | --- | --- | --- |

### 5.3 页面：`/admin/quotas` — 服务配额（管理面）

**组织表**：组织（名称 + id）、并发（"12 / 50"或"不限"）、服务（"3 / 20"或"不限"）、今日批量（"5 / 50"或"不限"）、Token 上限（"8192"或"不限"）、更新时间（相对）、更新人。行点击打开编辑对话框；历史图标打开变更历史抽屉。

**过滤栏**：名称搜索、限额状态（全部 / 有限 / 不限）、分页。

**编辑对话框**：四个字段（标注范围与"0 = 不限"）、预设行（Default / Starter / Growth / Enterprise — 一键填充字段）、内联校验（超范围显示"输入 0（不限）或 1–10000"式文案）、保存（PATCH）。保存显示成功 toast 并刷新行；**13305** 错误高亮出错字段。

**变更历史抽屉**（右侧）：该组织最近 20 条变更 — 时间、运营者、按维度旧 → 新（"并发：50 → 100"），来源于审计轨迹。

**状态**：加载骨架屏；空态（"还没有组织"）；错误（过期带重试）；无权限（标准样式，链接到 `/admin`）。

### 5.4 页面：`/quotas` — 我的配额（终端用户面）与配额条

**配额条**（组织上下文区，所有终端用户页面）：四个紧凑徽标 — "在途 12/50"、"服务 3/20"、"今日批量 5/50"、"Token ≤ 8192"（或每徽标"不限"）；≥ 80% 琥珀色、100% 红色；点击打开 `/quotas`。全部维度不限时配额条整体隐藏（默认态 — 无限制组织无视觉噪音）。

**`/quotas` 页**：四张卡片，各含维度名、通俗说明（"您的组织当前在途的请求数"）、用量/限额数字对、进度条（≥ 80% 琥珀、100% 红），token 上限为常量展示（"每个请求最多生成 8192 token"）。卡片下方：**申请提升**按钮（mailto 预填组织名）与"配额由平台运营者设置"的说明。

**状态**：加载；全部维度不限时的友好空态（"您的组织未设置任何限额 — 用量不受限制"）；错误（过期带重试）；用户面不存在无权限态（任何组织成员可见本组织配额）。

### 5.5 流程

1. **运营者限制吵闹的租户**（正常路径）：管理员 → `/admin/quotas` → 搜索组织 → 看到并发"142 / 不限" → 编辑对话框 → 设并发 50（或选 Growth 预设再调整） → 保存 → verdict 缓存 30 秒内传播 → 该组织第 51 个在途请求得到 13301 + `Retry-After: 1` → 租户配额条变红 → 租户打开 `/quotas` → 邮件申请提升 → 运营者审查后上调。
2. **租户为智能体定尺寸**：开发者 → `/quotas` → 读到"在途 12/50"与"Token ≤ 8192" → 把智能体客户端并发设为 40（留余量）、`max_tokens` 设为 4096 → 生产环境无配额错误。
3. **服务数守卫**：租户管理员 → 创建服务 → `CreateInferenceService` → 达到限额 → **13302**"您的组织已达到 20 个推理服务的上限…" → 租户移除未使用的服务或申请提升。
4. **批量洪水守卫**：租户脚本循环提交批量任务 → 当日第 N+1 次提交 → **13303** 带今日计数 → 脚本退避到午夜；配额条"今日批量"徽标展示用量。
5. **Token 上限守卫**：智能体发送 `max_tokens: 32768` 而组织上限 8192 → **13304**"每个请求上限 8192 token" → 客户端调低 `max_tokens`；未显式携带 `max_tokens` 的请求被静默钳制到 8192 并正常完成。
6. **收紧非破坏性**：运营者把服务 20 → 10 而组织运行着 14 个 → 不发生删除；下一次创建被拒 **13302**；组织自然下线 4 个服务；创建恢复。

## 6. API 表面影响

配额 RPC 扩展 **`tenancy`**（组织配额字段，管理面）并新增一个小的**用户前缀读取**（`GetMyQuota`）；执行契约扩展 `auth` 的 `VerifyAPIKey` verdict 与 `infer`/`batch` 创建路径。网关组件在仓库范围外 — 契约钉在此处（FR5.4）。

| RPC | 路由 | 前缀 | 状态 | 用途 |
| --- | --- | --- | --- | --- |
| `ListOrganizationQuotas`（扩展 `taas.tenancy.v1`） | `GET /api/v1/admin/quotas` | 管理 | **新增** | 按组织配额行及实时用量；分页、搜索、限额状态过滤 |
| `GetOrganizationQuota` | `GET /api/v1/admin/quotas/{organization_id}` | 管理 | **新增** | 单组织配额 + 用量 + 变更历史；未知组织 → 13306 |
| `UpdateOrganizationQuota` | `PATCH /api/v1/admin/quotas/{organization_id}` | 管理 | **新增** | 设置四个维度的任意子集；审计；坏值 → 13305 |
| `GetMyQuota` | `GET /api/v1/quotas` | 用户 | **新增** | 调用者组织配额及实时用量（脱敏 — 仅本组织） |
| `VerifyAPIKey`（`taas.auth.v1`） | 内部（网关 → `auth`） | 无 | **变更** | verdict 增加 `max_concurrent_requests`、`max_output_tokens_per_request`（组织级，D3） |
| `CreateInferenceService`（`taas.infer.v1`） | `POST /api/v1/inference-services` | 用户 | **变更** | 增加组织服务数检查；达限 → 13302 |
| `CreateBatchJob`（`taas.batch.v1`） | `POST /api/v1/batch/jobs` | 用户 | **变更** | 增加每日批量任务检查；达限 → 13303 |

**给架构师 agent 的契约说明**：

1. 四个配额字段位于组织行上（`organizations` 的增量 AutoMigrate 列，沿用 #6 的 `api_keys`/`accounts` 模式）；配额 RPC 是 tenancy 表面的管理绑定，不是新服务模块 — 但错误块（133xx）无论如何是新的（D4）。
2. 网关检查顺序有约束力：**速率限制（10037） → 配额并发（13301）/ token 上限（13304） → 资金（10502）**（§1.4）。token 上限检查在分发前校验/钳制 OpenAI 兼容 body 中的 `max_tokens`。
3. 在途跟踪是网关本地的（接受时递增，完成时递减，含断开）；用量快照 RPC 尽力而为中继（FR2.4）。重启重新推导或归零 — 已文档化、有界。
4. 批量每日计数器是 `COUNT(*) WHERE org AND created_at >= 本地午夜`（无新表）；时区为平台配置时区，在抽屉中文档化。
5. 13301 携带 `Retry-After: 1`（在途窗口很短）；13302/13303/13304 无 `Retry-After`（它们是配置错误，不是瞬态负载）。
6. 序列化惯例不变：成功 HTTP 200，业务错误为 `{"code": <int>, "message": "..."}`，int64 字段为 JSON 字符串。
7. 终端用户 `GetMyQuota` 必须在服务层强制组织限定（从会话取调用者组织），绝不信任客户端传入的组织 id。

错误码（`pkg/errors/codes.go`）：

| 条件 | 码 | 常量 | 说明 |
| --- | --- | --- | --- |
| 组织并发达到限额 | 13301 | `CodeQuotaConcurrencyExceeded` | **新增**（D4）— HTTP 429 + `Retry-After: 1` |
| 组织达到推理服务上限 | 13302 | `CodeQuotaServiceCountExceeded` | **新增**（D4）— 创建被拒 |
| 组织达到每日批量任务上限 | 13303 | `CodeQuotaBatchJobsExceeded` | **新增**（D4）— 创建被拒 |
| 请求 `max_tokens` 超出组织上限 | 13304 | `CodeQuotaOutputTokensExceeded` | **新增**（D4）— HTTP 400，指明上限 |
| 配额值超出范围 | 13305 | `CodeQuotaInvalid` | **新增**（D4）— 校验，指明维度 |
| 未知组织（配额读取） | 13306 | `CodeQuotaNotFound` | **新增**（D4） |
| 用户 realm 会话访问管理路由 | 10038 | `CodeRealmMismatch` | 复用 — realm 分离（FR5.1） |
| 会话无所需角色 | 10036 | `CodeForbidden` | 复用 — 权限拒绝（FR5.1） |

## 7. 验收标准

| # | 标准 | 级别 |
| --- | --- | --- |
| AC1 | `/admin/quotas` 渲染组织表，含并发 / 服务 / 今日批量（用量/限额或"不限"）、Token 上限、更新时间与更新人列，外加搜索、限额状态过滤与分页 | Nightwatch E2E |
| AC2 | 编辑对话框校验全部四个字段（范围 + "0 = 不限"文案）— 超范围值显示内联文案且服务端返回指明维度的 **13305**；四个预设一键填充字段且保存前仍可编辑 | Nightwatch E2E + FVT |
| AC3 | **并发执行（合成）**：组织上限 N 时，第 N+1 个并发请求被拒 **13301** 带 `Retry-After: 1`；请求完成释放槽位；不限（0）永不拒绝 | FVT（网关契约） |
| AC4 | **Token 上限执行（合成）**：组织上限 T 时，显式 `max_tokens > T` 被拒 **13304** 并指明上限；未携带 `max_tokens` 的请求被钳制到 T 并完成；`max_tokens ≤ T` 通过 | FVT（网关契约） |
| AC5 | **服务数守卫**：组织上限 N 个服务时，第 N+1 次 `CreateInferenceService` 返回带当前计数的 **13302**；收紧到运行数之下不触碰已存在服务 | FVT |
| AC6 | **批量每日守卫**：组织上限 N 个/日时，第 N+1 次 `CreateBatchJob` 返回带今日计数的 **13303**；已取消/失败任务仍计数 | FVT |
| AC7 | **检查顺序**：同时违反速率限制与配额的请求得到 **10037**（速率优先）；同时违反配额与资金的请求得到配额码（配额先于资金） | FVT（网关契约） |
| AC8 | **配额条与 `/quotas`**：终端用户控制台展示四个带用量/限额的徽标（≥ 80% 琥珀、100% 红），`/quotas` 页展示四张带通俗说明的卡片与申请提升 mailto；全部维度不限时配额条隐藏 | Nightwatch E2E |
| AC9 | **租户组织限定**：`GET /api/v1/quotas` 只返回调用者组织的配额；任何字段不泄露其他组织数据；租户面无配额变更路由 | FVT + Nightwatch E2E |
| AC10 | **变更历史与审计**：每次 `UpdateOrganizationQuota` 出现在审计轨迹（`quota.updated`，旧 → 新，运营者）与管理变更历史抽屉（最近 20 条） | FVT + Nightwatch E2E |
| AC11 | **传播窗口**：热路径配额变更在 verdict TTL 内（≤ 30 秒）执行；生命周期变更在下一次创建调用时；抽屉文档化两个窗口 | FVT |
| AC12 | **反向 realm 分离**：有效用户 realm 会话 token 访问 `GET /api/v1/admin/quotas` 被拒 **10038**；管理页无 `/api/v1/*` 调用、用户页无 `/api/v1/admin/*` 调用 | FVT + Nightwatch E2E |
| AC13 | 无所需角色的会话收到 **10036**，管理页展示标准无权限状态并带返回 `/admin` 链接 | Nightwatch E2E |
| AC14 | **状态**：两个页面提供指定的加载、空态（管理："还没有组织"；用户：全部不限的友好状态）与错误状态 | Nightwatch E2E |
