# 控制台表单规范 —— 必填分级与分区布局

| 属性 | 内容 |
| --- | --- |
| 功能点 | 控制台表单设计规范（两端所有创建/编辑表单） |
| 文档范围 | 表单向使用者说明"需要填什么"的需求分析与交互设计：三档必填等级、图例、编号区块、待填写提示行，以及渲染它们的共用组件 |

## 1. 背景

在平台上创建一个资源从来不是一个决定。部署一个推理服务需要大约二十五个输入，
注册模型五个，导入镜像八个，创建 Webhook 六个。在本规范之前，表单不说明平台究竟
需要哪些输入，于是使用者只能用最贵的方式获得答案：按猜测填一遍、提交、读报错、
再回来改。

这样做在三个层面上是亏的。

- **它掩盖了最省事的情形。** 这些输入中大多数已经携带平台会选的值。用集群默认值
  部署一个模型，实际只需手填一个字段 —— 服务名称 —— 而表单没有任何提示说明这点。
- **它惩罚了错误的字段。** 一个什么都不标注的表单，会让使用者去复核那十二个本来就
  已经正确的字段。
- **它掩盖了风险差异。** 两个看起来相似的字段，风险差别可以很大：引擎的
  `max-model-len` 留空是安全的（引擎自己选），`weightPath` 留空则不行（没有默认值
  可选）。只有逐字段的说明才能承载这种差别。

同样的三个事实也带来布局问题。二十五个输入的表单是一整面滚动的墙：没有分组、没有
节奏，也无法回答"我填完了吗"。

## 2. 需求

### 2.1 三档

控制台每个表单的每个输入，都严格属于其中一档，并由表单说明是哪一档：

| 档位 | 含义 | 使用者要做什么 |
| --- | --- | --- |
| **必填** | 不填则请求被拒绝。 | 填写。其中若干已由上下文预填（打开表单的那一行带来的模型与版本、加速卡筛出的镜像），因此真正需要手敲的字段很少。 |
| **默认** | 已有可用值：平台默认、集群上报的数字，或由其他字段推导的值。 | 什么都不做，除非该资源另有需要。有具体默认值时徽标直接写出（如「默认 · 4」）。 |
| **可选** | 留空是合法答案。 | 若不需要该功能则留空：留空表示"不启用"或"引擎沿用自身默认值"。 |

推导值单独用词 —— **自动推导** —— 而不给数字，因为数字随其他字段变化（单机副本的
卡数是 `TP × PP`），一个过期的数字比没有数字更糟。

### 2.2 需求条目

- **R1** 每个字段在标签旁渲染其档位徽标；徽标提示框解释该档含义。
- **R2** 三档在表单顶部解释一次，使第一个徽标出现时已被理解。
- **R3** 有具体默认值时徽标写出该值；由其他字段决定时写"自动推导"。
- **R4** 含多个概念组的表单拆成带编号的区块，每块带一行摘要说明它决定什么，并在
  其上方用细分隔线分开。
- **R5** 提交行写明仍缺什么（「待填写：服务名称」），填全后转为通过态，因此缺失的
  必填项在往返一次之前就可见。
- **R6** 对话框高于视口时，提交行吸底，待填写提示行无需滚动即可见。
- **R7** 字段标签不再带多余的"（可选）"后缀：徽标就是说明。
- **R8** 该规范由共用组件承载而非复制粘贴，因此新表单天然一致。

## 3. 设计

### 3.1 组件

`web/src/components/FormField.tsx` 提供全部词汇：

| 导出 | 渲染内容 |
| --- | --- |
| `ReqFlag` | 档位徽标（红「必填」、蓝「默认」、中性「可选」），档位说明作为提示框。 |
| `FieldLabel` | 标签 + 档位徽标，通过 `htmlFor` 绑定输入。 |
| `FormLegend` | 表单顶部展示一次的三档图例。 |
| `FormSection` | 一个编号区块：序号、标题、该块自身的档位、一行提示，以及上方的分隔线。 |
| `RequiredStatus` | 提交行中列出仍缺项、或确认已填全的那一行。 |

`Requirement`（`required` | `defaulted` | `optional`）是它们共用的类型，因此用
`FieldLabel` 写出的字段不可能漏标档位。

i18n 键放在 `form.*` 下（`form.req.*`、`form.reqHint.*`、`form.reqDefaultValue`、
`form.reqDerived`、`form.requiredMissing`、`form.requiredComplete`），而不是挂在最先
使用它的功能下：这套措辞讲的是表单，不是部署模型。

### 3.2 布局

```text
┌─ 面板 / 对话框 ─────────────────────────────────────────────┐
│ 标题                                            取消        │
│ ┌ 图例 ──────────────────────────────────────────────────┐ │
│ │ [必填] …   [默认] …   [可选] …                          │ │
│ └────────────────────────────────────────────────────────┘ │
│ ①  基础信息                                  该块决定什么  │
│ ────────────────────────────────────────────────────────── │
│    模型 [必填]              版本 [必填]                     │
│    …                                                       │
│ ②  副本与拓扑                                该块决定什么  │
│ ────────────────────────────────────────────────────────── │
│ ③  …                                                       │
│ ────────────────────────────────────────────────────────── │
│ 待填写：服务名称                 [取消] [部署]              │
└────────────────────────────────────────────────────────────┘
```

序号给出位置与进度感；提示行说明该块决定什么，使用者不必从字段反推分组；分隔线在
不套盒子的前提下把块分开。徽标是逐字段的，不是逐块的 —— 区块的档位只是摘要（一个
"必填"区块里仍然有可选字段）。

## 4. 验收标准

- **AC1** 必填字段不带值时被服务端拒绝，其徽标为「必填」。
- **AC2** 有平台默认值的字段在徽标中显示该值（「默认 · 4」），且可以不改动。
- **AC3** 可选字段留空可正常提交，并产生提示所描述的"不启用"或"引擎默认"行为。
- **AC4** 图例在每张表单中出现一次，并解释三档。
- **AC5** 多组表单的每个区块上方都有分隔线与一行提示；第一个区块没有分隔线。
- **AC6** 提交行按名称列出每个缺失的必填项，并在最后一项填上后切换为通过态。
- **AC7** 对话框高于视口时，提交行与其提示行在字段滚动时保持可见。
- **AC8** 表单标签不再以裸"（可选）"后缀结尾。
- **AC9** 表单在 375 px 宽度及 560 px 对话框内不出现横向滚动，两列网格的折行行为与
  之前一致。

## 5. 实现说明

- **网格轨道。** `.form-grid` 使用 `minmax(0, 1fr)` 而非 `1fr`，控件带 `min-width: 0`。
  裸 `1fr` 轨道不会缩小到内容最小宽度以下，所以一个较长的选项文案或占位符会把第二
  列挤出容器，并让对话框出现横向滚动条。
- **吸底提交行。** `.dialog > .dialog-actions` 使用 `position: sticky`，其负偏移抵消
  对话框内边距，并配不透明背景与上边框：提交行读作覆盖在滚动字段之上的页脚，而不是
  悬浮的条带。
- **提示行截断。** 待填写行限制为两行，因此缺六项的表单也不会把自己的按钮挤到第二行。
- **不只靠颜色。** 每个徽标都以文字承载档位，因此色盲用户与黑白截图下的区分仍然成立。
