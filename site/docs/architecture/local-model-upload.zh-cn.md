## 1. 缺口

此前模型列表只能通过公共 Hub 填充：`StartModelDownload` 从 ModelScope 或 HuggingFace 下载、写入权重挂载点并注册版本 —— 只要模型在 Hub 上，服务所需的一切都具备。但微调后的权重、离线环境内的模型、以及 Hub 上根本没有的模型，完全没有入口。

上传把这个缺口补上，并且复用同一个收尾：权重落盘，然后注册目录记录。上传得到的模型与下载得到的模型无法区分 —— 相同的权重路径形态、相同的部署路径、相同的删除清理。

## 2. 为什么是 HTTP 端点而不是 RPC

接口是 gRPC-JSON 转码的，转码无法承载二进制消息体。模型压缩包动辄几十 GB，放进 JSON 字段意味着先缓冲再 base64，在第一个字节落盘前就要占用三倍内存。因此上传是与镜像上传一样的纯流式端点：

```text
POST /api/v1/admin/models:upload     (multipart/form-data)
  file         压缩包（.tar、.tar.gz、.tgz 或 .zip）
  name         模型名称（必填）
  version      版本（可选）
  description  描述（可选）
```

**AD1 —— 先流式落到暂存文件，再交接。** 处理器用 `r.MultipartReader` 逐个读取 part，把 `file` 复制到临时文件，内存中只保留四个表单字段。`http.MaxBytesReader` 在读第一个字节前就限定请求大小，因此超大上传是被协议框架拒绝，而不是把磁盘写满。调用返回时暂存文件在所有路径上都会被删除。

**AD2 —— 解压归模型模块负责。** HTTP 层不认识压缩包：它只暂存字节并调用 `ModelUploadFunc`，由 `apps/taas-server` 接到 `model.Service.UploadModel`。服务层才有权重目录、仓储与审计记录器。

**AD3 —— 同步执行。** 镜像上传的先例是同步的，而进度本来也由浏览器上报（传输是客户端侧行为）。控制台用 `xhr.upload.onprogress` 显示上传百分比，在消息体发送完毕后切换为「正在解压并注册」—— 大模型下这个阶段有明显的停顿，需要如实告知。

## 3. 权重落在哪里

`<weightsDir>/<清洗后的名称>/<版本>/`

| 部分 | 规则 |
| --- | --- |
| `清洗后的名称` | 目录名中 `[A-Za-z0-9._-]` 之外的字符统一替换为 `-`（`/` → `-`，空格 → `-`），因此路径在命令行上永远不需要加引号 |
| `版本` | 请求的版本，未填则为 `upload-<YYYYMMDD-HHMMSS>`；`/`、`\`、`..` 与空格会被替换 |

记录的 `weight_path` 就是这个相对目录加结尾斜杠，与 Hub 下载完全一致（如 `Qwen__Qwen2.5-0.5B/`），也正是控制器挂载并把引擎指向的路径。

**AD4 —— 每个版本一个目录。** 同一模型的两个版本不能互相覆盖，因此版本是路径的一部分。重复上传已存在的版本会在解压之前被拒绝（见 AD6），已注册的权重永远不会被触碰。

## 4. 压缩包处理

| 格式 | 读取器 |
| --- | --- |
| `.tar` | `archive/tar` |
| `.tar.gz`、`.tgz` | `compress/gzip` + `archive/tar` |
| `.zip` | `archive/zip` |

以下规则中任何一条命中都会让整个上传失败，而不是跳过该条目：

- **禁止越界路径。** 含 `..` 的条目直接拒绝而非归一化处理：静默重定位会把文件解到运维人员并未打包的位置，而模型压缩包里的 `..` 只可能是错误或攻击，不可能是布局选择。绝对路径会按构造被限制在目标根目录内。
- **禁止链接、设备与 fifo。** 只解压普通文件与目录 —— 符号链接是经典的越界手段。
- **限制膨胀。** `maxUploadExtractedBytes`（4 TiB）、`maxUploadEntryBytes`（512 GiB）与 `maxUploadFiles`（200 000）阻止压缩炸弹写满权重存储。
- **空压缩包视为错误。** 没有文件的压缩包会注册一个无法服务的模型。
- **失败即清理。** 解压一半的目录比没有更糟 —— 之后的部署会把它当成模型来服务 —— 因此任何失败都会删除目标目录。

**AD5 —— 权限与下载器一致。** 目录 `0750`、文件 `0644`，正是 Hub 下载留下的权限。权重目录是引擎 Pod 的共享只读挂载，而引擎 Pod 未必以服务进程的用户运行；把上传文件写成 `0600` 会得到一个能启动却读不到权重的服务。

**AD6 —— 在解压前就拒绝不可能成功的注册。** 同名模型若已绑定 Hub id 则是另一种东西（`checkHubBinding`），而版本已存在则要么被覆盖、要么（配合陈旧目录清理）被删除。两个检查都放在最前：开销很小，并且在答案已经是否定的时候不让字节落盘。

## 5. 注册

调用 `RegisterModelOrCreateVersion(name, description, "", version, weightPath)` —— 与下载任务同一个方法：

- 没有同名模型 → 创建模型及其第一个版本；
- 模型存在、版本是新的 → 追加版本；
- 版本已存在 → `10102 MODEL_EXISTS`（前面已先行拒绝，见 AD6）。

随后记录一条审计事件（`model.upload`，资源 `model`），使这次入库与下载、删除一样可追溯。

删除上传的模型无需改动：`DeleteModel` 会删除各版本指向的权重目录 —— 这也是上传只写 `<weightsDir>` 内部的原因。

## 6. 错误

所有上传失败都走统一响应封装。业务错误码保持原义，意外失败一律映射为 `10104 MODEL_PATH_INVALID`。

| 错误码 | 名称 | 触发条件 |
| --- | --- | --- |
| 10104 | `MODEL_PATH_INVALID` | 缺少名称、名称/版本/描述超长、压缩包扩展名未知、压缩包不可读、条目越界、膨胀超限、空压缩包、未配置权重目录 |
| 10102 | `MODEL_EXISTS` | 模型已绑定 Hub id，或该版本已存在 |
| 10101 | `MODEL_NOT_FOUND` | 不会出现 —— 缺失的模型会被创建 |

## 7. 控制台

`/admin/models` 在下载面板与注册动作旁新增 **本地上传**。`UploadModelDialog`：

- 文件选择器限定四种扩展名；选择文件后若尚未填写名称，则用文件名（去掉扩展名）自动填入模型名称；
- 名称（必填）、版本（可选 —— 由服务端生成时间戳）、描述（可选）；
- 由 `xhr.upload.onprogress` 驱动的进度条，随后进入「正在解压并注册」状态；
- 成功后关闭弹窗并刷新页面，新模型即可立即部署。

## 8. 验收标准

1. 上传模型目录的 `.tar.gz`：解压到 `<weightsDir>/<清洗名称>/<版本>/`，并以该相对路径注册版本。
2. `.zip`、`.tar`、`.tgz` 同样可用。
3. 含 `../x` 的压缩包被拒绝，且不会在权重根目录之外写入任何内容。
4. 扩展名未知或没有文件的压缩包被拒绝。
5. 对已存在的「名称+版本」重复上传被拒绝，且第一个版本的文件保持不变。
6. 解压失败不会留下残留目录。
7. 上传的文件对引擎 Pod 可读（文件 `0644`，目录 `0750`）。
8. 删除上传的模型会同时删除其权重目录。
9. 未配置权重目录的安装会给出明确错误，而不是接收无法保存的字节。

已在 https://taas.sudoinfotech.com 实际验证：通过控制台端点上传 `.tar.gz` 冒烟模型（`files: 3`，`weightPath: Upload-Smoke-Test/v2/`），`/data/weights/Upload-Smoke-Test/v2/` 下出现解压后的文件且权限为 `0644`，模型列表出现该记录，随后删除模型并清理权重。
