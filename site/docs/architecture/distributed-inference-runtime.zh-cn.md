## 1. 运行时由什么构成

| 组件 | 长度 |
| --- | --- |
| **KServe**（`serving.kserve.io`，LLM 服务运行时及其预置） | CRD、工作负载（leader-worker set）、暴露工作负载的 `Service`、自动伸缩 |
| **数据面 Gateway**（Envoy Gateway） | 公网域名、TLS、Wasm 链（API key、配额、计量） |
| **平台控制器** | 引擎 Pod（镜像、参数、设备、权重、环境变量）、多 Pod 副本被作为一个整体放置的 Pod 组 |
| **模型路由器** | 唯一知道模型是自托管还是外部的一跳，也是平台请求路径被决定的地方 |

一个服务对应一个对象 `LLMInferenceService`，它承载了一个服务的全部内容：模型、副本数、Pod 模板与伸缩策略。字段级细节见[LLMInferenceService 服务拓扑](./llminferenceservice-serving-topology.md)；面向运维的版本见[服务运行时](../guides/serving-runtime.md)。

## 2. 为什么选这套栈，以及被否决的方案

有三条硬性需求否掉了替代方案。每条都是平台必须做的事，不是偏好：

1. **一个服务一个对象，不论其形态。** 平台按 id 跟踪服务，并只向集群交付一个对象。若某种栈的形态随拓扑变化（一个 Pod 一个对象、一个副本组又一个对象、路由再一个对象），那么所有消费方——配额、控制台、日志、计量——都必须按形态分支。KServe 的 `LLMInferenceService` 把单 GPU Pod、leader-worker set 以及 prefill/decode 对表达为同一个对象的字段。
2. **放置权留在集群，不留给平台。** 多 Pod 副本要么整体被放置，要么不启动；这是一个拿着集群空闲加速卡容量做出的 gang 决策。因此平台写出一个 Pod 组，由集群调度器做决定，而不是自己去当调度器。
3. **平台按模型路由，工作负载按副本应答。** 请求里带的是模型名；平台的这条路由把它交给模型路由器，路由器把模型解析成“哪个服务答它”，再转给该服务的工作负载 `Service`。这个工作负载的哪个副本应答，是 `Service` 自己的负载均衡，平台因此不必知道一个引擎跑了几个 Pod。

还有第四条需求说明了为什么下面的两跳拆分值得：终结公网域名的那一层才是知道 API key 的那一层，而知道模型的那一层才能路由一个请求。把两者合并意味着模型自己的路由被挡在 key 校验之后，那就得再来一次校验或者开一个旁路。

被否决的方案，以及为什么这不是一个难以取舍的决定：

- **平台自持一个服务对象，并由平台控制器包办一切。** 这是平台原本的做法：Pod 形态由平台自己写。这意味着每个放置决策都是平台的，平台就变成了它不想成为的调度器。
- **每个服务一个 Gateway。** 实际做法是每个推理命名空间一个 Gateway；若改成每服务一个，就在最要紧的那一层——公网层——重新引入了"每个阻塞点一个对象"的问题。
- **每个模型一条 `HTTPRoute`，不管由谁写。** 这条路由的后端只能是运行时的池，而本集群的 Gateway 不服务这种后端：路由永远拿不到 `Accepted`，于是模型明明通过自己的工作负载 `Service` 在正常服务，对象却被报成未就绪。平台只写一条兜底路由，模型路由器把模型解析成服务，因此根本不存在按模型的路由。
- **每服务一个独立的伸缩器对象**（`PodAutoscaler` 那种形态）。那是第二个要与第一个保持同步的对象，而它的目标正是上一条已经归运行时所有的那个对象。策略写在服务上，伸缩器跟着工作负载走。
- **内部一跳再做一次校验。** 第一跳已经校验了 key、配额与计量，第二跳若再校验就需要一个平台并不签发的可信令牌，因此第二跳是集群内的明文 HTTP，且内部监听器不可从外部到达。后半句是部署要求而不是约定：一个带公网地址的内部监听器就是一条 key 旁路。

## 3. 平台负责什么、不负责什么

| 平台决定 | 理由 |
| --- | --- |
| Pod：镜像、引擎参数、设备、权重挂载、环境变量、探针 | 模型、它的调优与它的限额是我们的 |
| 多 Pod 副本的 Pod 组 | 一个只放下一半的副本不该占住它用不上的 GPU |
| 自动伸缩关闭时的 `spec.replicas` | 手工扩缩容就是服务最终拿到的副本数 |
| 模型的 URI 与名字 | 权重布局与对调用方可见的名字是租户的契约 |
| 唯一一条数据面路由与 key 校验 | 公网路径与一次请求的准入代价是平台的 |

| 不属于平台 | 理由 |
| --- | --- |
| 哪个副本应答请求 | 那是工作负载 `Service` 的事，平台不需要在这里推理 |
| 工作负载的种类、身份、滚动更新 | 随拓扑改变种类的服务对象正是平台拒绝跟踪的东西 |
| 伸缩器的算法与触发器 | 策略是我们的，机制是工作负载的 |
| 工作负载 `Deployment` 与暴露它的 `Service` | 运行时从平台已经写好的对象里把它们写出来 |
| 第二跳上的再校验、配额或计量 | 第一跳已经做了；再校验需要平台并不签发的令牌 |
| 平台自己的调度器 | 放置是带着集群状态的集群决策；平台调度器会输给它 |

真正要守的那条线是：平台拥有**一个服务是什么**以及**准入一次请求要花多少**；集群拥有**Pod 去哪里**，运行时拥有**哪个副本应答**。

## 4. 控制面与数据面

```
控制面（平台）                              数据面（集群内）
────────────────────────────                ───────────────────────────────
infer 模块 → 变更事件 → MQ  ─────▶  控制器：一个 LLMInferenceService
                                        │ + 需要 gang 时的 Pod 组
                                        ▼
                                    KServe：工作负载 + 它的 Service
                                        │
公网域名 ◀── Gateway ◀── 路由 ─────────▶  模型路由器 → 工作负载 Service
```

控制面从不与 Pod 说话。它把一个服务收敛成一个对象就停下。数据面从不与数据库说话。它用手上已有的、来自该对象的状态应答请求。两者只在一个地方汇合：控制器写的、运行时读的那个 `LLMInferenceService`。再多一个汇合点就是多一个要保持同步的东西，而漂移的永远是它。

控制面的故障是控制台能展示的那一类：一个收敛不了的服务、一个不接纳的 key、一个不是 `kserve` 的 scheme。数据面的故障是请求能展示的那一类：余额耗尽带来的 429、没有副本就绪时的 503。把两者分开，各自都能在不需要对方的情况下被排查。

## 5. 服务自己的对象

控制器每次 upsert 写一个对象，销毁时删除同一样东西：

- `spec.model{name, uri}` —— 调用方作为 `model` 发送的名字，权重被挂载到的 URI（`pvc://<pvc>/<weight path>`）；
- `spec.replicas` —— 副本数，自动伸缩关闭时由平台钉住；
- `spec.template` —— 引擎 Pod，平台自己的容器按名字覆盖到预置的 model server 上；
- 一个副本多于一个 Pod 时的 `spec.worker` 与 `spec.parallelism.data`；
- 拓扑为 prefill/decode 时的 `spec.prefill{replicas,template}`；
- 不写 `spec.router` —— 路由归平台，不向运行时索取模型路由；
- `spec.storageInitializer.enabled: false` —— 权重由平台自己挂载。

Pod 组是第二个对象，只在多 Pod 副本且集群调度器支持 gang 时写；单 Pod 副本按 Pod 放置。Pod 组带上服务的属主标签，因此被删掉的服务会把它一起带走。（字段名及其理由见[拓扑文档](./llminferenceservice-serving-topology.md)，本页不重复。）

## 6. 运行时健康与投影

运行时页面读的是一份投影，不是集群：

1. 控制器轮询推理命名空间里 KServe 控制面的 Deployment 与数据面 Gateway 的就绪状态，把快照发到运行时自己的 MQ 主题上；
2. 运行时模块把快照留在内存里，形状与加速卡清点一致，页面由它来回答；
3. 消失的组件在下一个快照里消失，跟清点一样是自愈的形状：一行陈旧数据活不过它的来源。

就绪的含义是"它的 Deployment 报告的可用副本数不少于期望副本数"——每个组件用同一把尺子，因此一个被列进页面的组件不会与控制台的意见不一致。

**scheme。** scheme 是 `kserve`，且它是默认值。`plain` 意味着"一个 Deployment 加一个 Service，没有 KServe 对象"，是 CRD 缺席的集群或单元测试用的退路；`plain` 下没有运行时写出的工作负载，两种模式下也都没有按模型的路由。它不是同一个对象的第二种模式，控制台在页面上如实说明，而不是给出一个仿佛有得选的开关。

## 7. 配置

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `runtime.gateway.namespace` | 控制器所在命名空间 | 平台的数据面路由所挂靠的那个数据面 `Gateway` 的命名空间 |
| `runtime.gateway.name` | `taas-inference`（发布名） | Gateway 的名字；Envoy Service 被钉成它 |
| `runtime.gateway.deployment` | 与 `name` 相同 | 为该 Gateway 提供后端的 Deployment，用于组件健康 |
| `controller.scheduling.schedulerName` | 空 | `volcano` 打开 gang 调度；空则把放置交给集群默认 |

服务端写进数据面路由的那个 Gateway，与那条路由以及模型路由器所寻址的 Envoy Service，必须指向同一个 Gateway。不一致不会让路由自报问题：控制台显示服务 `Ready`、请求照样 404，这也是 `helm template` 把两者都点名的一个原因。

## 8. 错误

运行时面用平台的错误码；运维会撞见的几个：

| 码 | 名字 | 何时 |
| --- | --- | --- |
| 12901 | `CodeRuntimeUnavailable` | 集群或 KServe 控制面不可达；运行时页面显示没有组件，scheme 保持原样 |
| 12902 | `CodeRuntimeSchemeInvalid` | scheme 不是 `kserve` 或 `plain` |
| 12905 | `CodeRuntimeEngineUnsupported` | 引擎不在平台支持的集合里 |
| 12909 | `CodeRuntimeRouteNotPublished` | 服务已 `Ready` 但还没有为它发布出路由 |

## 9. 验证

本次实际跑了什么：`go build ./...`、`go vet ./...`、`go test ./...`（运行时与控制器的单测覆盖投影的形状与服务对象的字段——断言见拓扑文档）、在数据面、网关插件与模型路由器都打开的 `deploy/helm/go-taas` 上跑 `helm template` / `helm lint`，以及为文档索引跑 `node site/scripts/build-docs-manifest.mjs --check`。

也在一套真实集群上用真实的模型与它自己的镜像观测过：对象变成 `Ready`，工作负载 `Deployment` 与它的 `Service` 都在，一个引擎 Pod 在服务，走公开主机名的一次补全能返回生成的文本。集群上的核对就是那次请求，加上对同一个服务跑 `kubectl get llminferenceservice,podgroup -A`。

## 10. 局限，明说

- 多 Pod 副本要有能 gang 的调度器，以及若干台有空闲设备的机器；两者都不在的集群会让服务停在 `Pending`、Pod 组停在 `Unschedulable`，这是诚实的状态而不是一个重试循环。
- PD 要有能把 prefill 从 decode 里拆出来的引擎；prefill 那一半有自己的副本数和自己的调优，所以一个 PD 服务是两段角色各自要弄对，而不是一段。
- 运行时的收集是轮询：在就绪与不就绪之间来回跳的组件，新鲜度只到轮询间隔，控制台会说出快照是什么时候取的，而不是假装它是实时的。
